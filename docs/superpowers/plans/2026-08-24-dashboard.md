# PifPaf Pulse — срез 6: дашборд

> **Для исполнителя:** используй `superpowers:subagent-driven-development` (рекомендуется)
> или `superpowers:executing-plans`. Шаги размечены чекбоксами (`- [x]`).

**Цель:** блогер открывает `/app` и видит аналитику: строку KPI, график динамики
просмотров, топ-3 рилса и гистограмму «когда лучше постить». С карточки в ленте
можно провалиться в `/app/reels/:id` — экран с графиком роста по снапшотам,
который и продаёт всю идею «данные обновляются сами». В `/app/settings` он правит
имя и инстаграм-хендл, меняет пароль и видит свои цифры за всё время.

**Архитектура:** данные считаются тремя новыми запросами сырым SQL в
`src/db/queries/`. Серверные компоненты зовут их напрямую, форматируют всё
время и все числа **на сервере** и передают графикам готовые строки. Графики —
Recharts, а значит клиентские; они получают только примитивы и ничего не
вычисляют. Экран рилса — серверный компонент поверх типизированного пути Drizzle.

**Тех.стек:** Next.js 16 (App Router), React 19, Recharts (**новая зависимость,
проверяется задачей 1**), Tailwind 4, сырой SQL через `db.execute`, Vitest.

**Спека:** [`PLAN.md`](../../../PLAN.md) §8 (SQL и таймзона), §9 (эндпоинты),
§10 (`/app`, `/app/reels/:id`), §12 (чек-лист очеловеченности).

**Предыдущий срез:** [`2026-08-24-feed.md`](2026-08-24-feed.md) — закрыт и слит в `main`.

## Два бага в SQL из спеки, которые чиним сразу

Запрос динамики в `PLAN.md` §8 написан так:

```sql
SELECT date_trunc('day', s.captured_at AT TIME ZONE 'Europe/Moscow') AS day,
       SUM(s.views) AS total_views
FROM reel_snapshots s JOIN reels r ON r.id = s.reel_id
WHERE r.user_id = $1 GROUP BY 1 ORDER BY 1;
```

**Баг 1 — двойной счёт.** `SUM(s.views)` складывает снапшоты, а не рилсы. Рилс,
опрошенный утром (1000 просмотров) и вечером (1200), даст за день 2200 — число,
которого не существует. Свежий рилс опрашивается раз в час (§7), то есть в первые
сутки он посчитается двадцать четыре раза. Правильно: взять **последний снапшот
каждого рилса за каждый день** и только потом складывать.

**Баг 2 — дыры.** В день, когда часть рилсов не опрашивалась, сумма падает.
Суммарные просмотры не умеют убывать, поэтому такой график читается как сломанный.

Оба чинятся в задаче 3. Спеку тоже поправить — задача 15.

## Глобальные ограничения

- **ORM — Drizzle, не Prisma.** Аналитические запросы — сырым SQL в `src/db/queries/`,
  отдельными файлами с комментариями. Это витрина навыка, а не деталь реализации.
- **Нет данных — это `—`, а не `0`.** Ноль валиден и выглядит иначе.
- **Всё время в интерфейсе и в группировках — `Europe/Moscow`**, через `MOSCOW_TZ`.
  `date_trunc` без `AT TIME ZONE` сдвинет гистограмму на три часа, и пик «когда постить»
  уедет с 20:00 на 17:00. Проверяющий из индустрии прочтёт это как поломку.
- **Изоляция данных:** каждый запрос и эндпоинт фильтрует по `user_id` сессии;
  чужая запись — **404**, не 403.
- **Тексты интерфейса — по-русски, на «ты»**, в тоне pifpafai.com. Ошибки —
  человеческим языком, без кодов.
- **Мобильная вёрстка обязательна** — проверять будут с телефона.
- **Netlify free: 10 секунд на функцию.** Ни один запрос не ждёт Apify.
- **`db.execute` не приводит типы:** `bigint`, `numeric` и `timestamptz` приходят
  **строками**, `int` и `bool` — нет. Каждый новый сырой запрос обязан приводить
  их сам, как это делает `list-reels.ts`. Типизированный `db.select()` не расходится.
- **Recharts — единственная новая зависимость среза.** Больше ничего не ставим.
- **Файлы с top-level `await` или `import.meta` — расширение `.mts`.**

`src/db/queries/stats-timeseries.ts`:

```ts
import { sql } from 'drizzle-orm'
import { db } from '@/db'
import { MOSCOW_TZ } from '@/lib/time/moscow'

export type TimeseriesRange = '7d' | '30d' | 'all'
export type TimeseriesPoint = { day: string; totalViews: number }

const DAYS: Record<TimeseriesRange, number | null> = { '7d': 7, '30d': 30, all: null }

/**
 * Суммарные просмотры по дням для графика динамики.
 *
 * Запрос из PLAN.md §8 содержал две ошибки, обе чинятся здесь.
 *
 * ПЕРВАЯ: он складывал `s.views` по снапшотам. Рилс, опрошенный утром на 1000
 * и вечером на 1200, давал за день 2200 — число, которого не существует.
 * Свежий рилс опрашивается раз в час (§7), то есть за первые сутки посчитался
 * бы двадцать четыре раза. Лечится `DISTINCT ON (reel_id, day)`: берём
 * последний снапшот КАЖДОГО рилса за КАЖДЫЙ день и только потом складываем.
 *
 * ВТОРАЯ: в день, когда часть рилсов не опрашивалась, сумма проваливалась.
 * Суммарные просмотры не умеют убывать, и такой график читается как сломанный,
 * а дыры при адаптивном расписании §7 неизбежны: месячный рилс опрашивается
 * раз в неделю. Лечится классическим для Postgres приёмом gaps-and-islands:
 * `count()` по возрастанию дней растёт только там, где значение есть, и потому
 * нумерует «острова»; `first_value` внутри острова протягивает последнее
 * известное значение вперёд по дырам.
 *
 * Дни ДО первого снапшота рилса отбрасываются: тянуть назад нечего, и рилс,
 * добавленный вчера, не должен приписывать себе прошлую неделю.
 */
export async function statsTimeseries(
  userId: string,
  range: TimeseriesRange = '30d',
): Promise<TimeseriesPoint[]> {
  const days = DAYS[range]

  // Нижняя граница: либо «сегодня минус N дней», либо самый ранний снапшот.
  // Считается в SQL, а не в JS: границей календаря должен быть московский день,
  // а не день часового пояса машины, где выполняется Node.
  const from = days
    ? sql`(now() AT TIME ZONE ${MOSCOW_TZ})::date - ${days - 1}::int`
    : sql`(
        SELECT MIN((s.captured_at AT TIME ZONE ${MOSCOW_TZ})::date)
        FROM reel_snapshots s
        JOIN reels r ON r.id = s.reel_id
        WHERE r.user_id = ${userId}
      )`

  const rows = await db.execute(sql`
    WITH bounds AS (
      SELECT generate_series(
        ${from},
        (now() AT TIME ZONE ${MOSCOW_TZ})::date,
        INTERVAL '1 day'
      )::date AS day
    ),
    per_reel_day AS (
      SELECT DISTINCT ON (s.reel_id, (s.captured_at AT TIME ZONE ${MOSCOW_TZ})::date)
             s.reel_id,
             (s.captured_at AT TIME ZONE ${MOSCOW_TZ})::date AS day,
             s.views
      FROM reel_snapshots s
      JOIN reels r ON r.id = s.reel_id
      WHERE r.user_id = ${userId}
      ORDER BY s.reel_id,
               (s.captured_at AT TIME ZONE ${MOSCOW_TZ})::date,
               s.captured_at DESC
    ),
    grid AS (
      SELECT r.id AS reel_id, b.day
      FROM reels r CROSS JOIN bounds b
      WHERE r.user_id = ${userId}
    ),
    islands AS (
      SELECT g.reel_id, g.day, p.views,
             count(p.views) OVER (PARTITION BY g.reel_id ORDER BY g.day) AS island
      FROM grid g
      LEFT JOIN per_reel_day p ON p.reel_id = g.reel_id AND p.day = g.day
    ),
    carried AS (
      SELECT reel_id, day,
             first_value(views) OVER (PARTITION BY reel_id, island ORDER BY day) AS views
      FROM islands
    )
    SELECT to_char(day, 'YYYY-MM-DD') AS day, SUM(views) AS total_views
    FROM carried
    WHERE views IS NOT NULL
    GROUP BY day
    ORDER BY day
  `)

  const raw = (Array.isArray(rows) ? rows : ((rows as { rows?: unknown[] }).rows ?? [])) as Record<
    string,
    unknown
  >[]

  // total_views — сумма BIGINT, а значит строка. См. таблицу типов в AGENTS.md.
  return raw.map((row) => ({
    day: String(row.day),
    totalViews: Number(row.total_views),
  }))
}
```

> **Запрос не прогонялся автором плана** — базы под рукой не было. Он выверен
> логически, но самое вероятное место отказа известно: подстановка `${MOSCOW_TZ}`
> связанным параметром внутрь `AT TIME ZONE`, `DISTINCT ON` и `ORDER BY`.
> Postgres принимает `timestamptz AT TIME ZONE $1`, но если драйвер или
> планировщик заупрямятся — не подставляй строку в текст запроса (это открытая
> дверь для инъекции даже с константой), а импортируй `MOSCOW_TZ` и передай его
> через `sql.raw` **только** после явной проверки, что значение — литерал из
> `src/lib/time/moscow.ts`, а не что-то извне. Второе вероятное место —
> `generate_series` с границами-датами: при пустой выборке `MIN(...)` даёт
> `NULL`, и серия обязана вернуть ноль строк, а не упасть.

### Задача 11: Профиль — чистые функции и аватар

**Файлы:**
- Создать: `src/lib/profile/validate.ts`, `src/components/ui/avatar.tsx`

**Интерфейсы:**
- Отдаёт наружу:
  ```ts
  /** Текст ошибки для интерфейса или null, если имя годится. */
  function validateDisplayName(raw: string): string | null
  /** '@name', 'instagram.com/name/', 'name' → 'name'. */
  type HandleResult = { ok: true; handle: string | null } | { ok: false; reason: string }
  function normalizeInstagramHandle(raw: string): HandleResult

  function Avatar(props: { name: string; size?: number; className?: string }): JSX.Element
  ```
  Используется задачами 12 и 13.

**Почему хендл нормализуется, а не принимается как есть.** Блогер скопирует его
из шапки профиля вместе с собачкой, или вставит ссылку целиком, или ссылку
с хвостом `?igsh=` от кнопки «Поделиться» — ровно те же формы, что уже разобраны
для ссылок на рилсы в `src/lib/instagram/normalize-url.ts`. Посмотри туда:
структура ответа (`{ ok: true, ... } | { ok: false, reason }`) и тон сообщений

### Задача 12: Эндпоинты профиля и смены пароля

**Файлы:**
- Создать: `src/app/api/settings/route.ts`, `src/app/api/settings/password/route.ts`

**Интерфейсы:**
- Использует: `requireSession`, `validateDisplayName`, `normalizeInstagramHandle`
  (задача 11), `validatePassword`, `hashPassword`, `verifyPassword`
  (`src/lib/auth/password.ts`, готовы с среза 1), `ok`/`fail`/`handleError`.
- Отдаёт наружу:
  ```
  PATCH /api/settings           { displayName?, instagramHandle? } → 200 { displayName, instagramHandle }
  POST  /api/settings/password  { currentPassword, newPassword }   → 200 { ok: true }
  ```
  Используется задачей 13.

**Смена пароля обязана проверять текущий.** Без этого украденная или забытая
на чужом устройстве сессия превращается в захват аккаунта: достаточно открыть
настройки и задать новый пароль. Проверка текущего — единственное, что стоит
между угнанной вкладкой и потерей доступа.

**Чего мы при этом НЕ можем и о чём надо сказать честно.** Сессия — подписанный
JWT без серверного хранилища (`src/lib/auth/session.ts`). Отозвать выданные
токены нечем, поэтому смена пароля **не** выкидывает с других устройств:
старый токен продолжит работать до истечения. Это осознанный компромисс
архитектуры, а не недосмотр — записать его в хвосты `AGENTS.md` задачей 15
и **не** писать в интерфейсе, что другие устройства разлогинены.

- [x] **Шаг 1: `PATCH /api/settings`**

Шаблон брать с `src/app/api/reels/[id]/sync/route.ts` — `export const runtime = 'nodejs'`,
`requireSession()` первым, `try/catch` с `handleError`.

Порядок и правила:
1. `requireSession()`.
2. Разобрать тело; оба поля необязательные — пришло только имя, меняем только имя.
3. `validateDisplayName` и `normalizeInstagramHandle`; при ошибке — `fail(текст, 400)`.
4. `db.update(users).set({...}).where(eq(users.id, session.userId))` — **всегда**
   по `userId` из сессии, никогда по идентификатору из тела запроса.
5. Вернуть новые значения, чтобы форма не гадала.

> Идентификатор пользователя берётся ТОЛЬКО из сессии. Приняв его из тела,
> получаем правку чужого профиля по номеру — та же ошибка, от которой
> `assertOwned` защищает рилсы.

- [x] **Шаг 2: `POST /api/settings/password`**

1. `requireSession()`.
2. Прочитать `currentPassword` и `newPassword`.
3. `validatePassword(newPassword)` — переиспользовать, не писать свои правила.
   Он уже знает про минимальную длину и про то, что bcrypt молча режет вход
   на 72 байтах, а кириллица занимает по два.
4. Достать `passwordHash` пользователя, `verifyPassword(currentPassword, hash)`.
   Не сошлось — `fail('Текущий пароль не подошёл', 400)`.
5. Новый пароль совпадает с текущим — `fail('Новый пароль совпадает с текущим', 400)`.
6. `hashPassword(newPassword)`, записать.

> Сообщение об ошибке — человеческим языком, без кодов (§12). И не подсказывать
> лишнего: «Текущий пароль не подошёл» достаточно, разъяснять правила
> несуществующему злоумышленнику незачем.

- [x] **Шаг 3: Проверить руками**

`curl` в Windows-консоли **портит кириллицу в теле запроса** — можно получить
и ложную ошибку, и ложный успех. Проверять только клиентом на Node; одноразовый
скрипт положить рядом и удалить после, не коммитя.

Что проверить:

| Запрос | Ожидаем |
|---|---|
| `PATCH` гостем | 401 |
| `PATCH` с пустым именем | 400 с русским текстом |
| `PATCH` с `@Хендл` кириллицей | 400, причина понятная |
| `PATCH` только с хендлом | имя не затёрлось |
| Смена пароля с неверным текущим | 400, пароль в базе не изменился |
| Смена пароля верная | 200, старый пароль больше не подходит на `/api/auth/login`, новый подходит |

Последняя строка — единственная, доказывающая, что смена действительно
произошла. Проверить обе половины: и что старый перестал работать, и что новый начал.
